Panoramica dell'Architettura di Sistema

Invisible è un sistema distribuito composto da un'applicazione mobile Flutter e quattro microservizi Go orchestrati tramite Docker Compose su VPS Linux. La comunicazione tra client e server avviene esclusivamente attraverso tunnel WireGuard cifrati, con un ulteriore layer TLS 1.3 gestito da nginx come reverse proxy.

1.1 Principi Architetturali

  • Zero Knowledge Server — il server non possiede mai informazioni sufficienti a decifrare le comunicazioni
  • Defense in Depth — tre layer di cifratura indipendenti e sovrapposti
  • Minimal Trust — ogni componente può essere compromesso senza esporre il sistema completo
  • Local-First Cryptography — le chiavi nascono e muoiono sul dispositivo, mai trasmesse
  • Microservices Isolation — ogni servizio ha scope limitato, nessun servizio ha visibilità globale

Architettura Microservizi Server

3.1 mesh-gateway (:8080)

Gestisce la registrazione dei dispositivi nella rete WireGuard e l'assegnazione degli indirizzi IP mesh. Autentica ogni richiesta tramite firma Ed25519.

Endpoints

MetodoPathDescrizioneAuth
POST/v1/mesh/registerRegistra public key WireGuard, riceve IP mesh 10.7.x.xEd25519 header
GET/v1/mesh/peersLista peer WireGuard per la meshEd25519 header
DELETE/v1/mesh/unregisterRimuove dispositivo dalla meshEd25519 header

Logica di autenticazione Ed25519

// Header richiesta:
// X-Identity-Key: base64(ed25519_public_key)
// X-Timestamp: unix_timestamp
// X-Signature: base64(ed25519_sign(timestamp + body_hash))

func verifyRequest(r *http.Request) bool {
    pubKey := base64.Decode(r.Header.Get("X-Identity-Key"))
    ts     := r.Header.Get("X-Timestamp")
    sig    := base64.Decode(r.Header.Get("X-Signature"))
    msg    := ts + hashBody(r.Body)
    return ed25519.Verify(pubKey, []byte(msg), sig)
}

3.2 signaling (:8081)

Microservizio WebSocket per il routing dei messaggi SDP/ICE durante la negoziazione WebRTC. Non interpreta il contenuto dei messaggi — li instrada semplicemente al destinatario corretto identificato dal suo IP mesh.

Protocollo WebSocket Signaling

// Messaggi in formato JSON (cifrati E2E, il server vede solo routing):
{
  "type": "offer" | "answer" | "ice-candidate" | "call-invite" | "call-reject" | "call-end",
  "to":   "10.7.x.x",          // IP mesh destinatario
  "from": "10.7.x.x",          // IP mesh mittente
  "data": "base64_cifrato"     // SDP o ICE candidate, cifrato
}

3.3 relay (:8082)

Microservizio WebSocket per la consegna asincrona dei messaggi E2E. Mantiene una coda per i messaggi destinati a utenti offline per un massimo di 7 giorni. Il relay vede solo ciphertext opaco — non ha accesso al contenuto dei messaggi né alle identità reali dei comunicanti.

Struttura messaggio relay

// Outer payload (visibile al relay):
{
  "to":      "10.7.0.8",            // IP mesh destinatario
  "from":    "10.7.0.5",            // IP mesh mittente
  "payload": "base64(json({         // ciphertext opaco
    \"ciphertext\": \"base64_bytes\",
    \"header\":     \"base64_header\"
  }))"
}
// Il relay non può decifrare payload — contiene Double Ratchet ciphertext

Coda offline

type QueuedMessage struct {
    ID        string
    To        string
    From      string
    Payload   []byte
    Timestamp time.Time
    TTL       time.Duration // 7 giorni
}
// I messaggi scaduti vengono eliminati automaticamente
// Non c'è persistenza a lungo termine — privacy by design

Protocollo Crittografico

4.1 Generazione dell'Identità Crittografica

Al primo avvio, CryptoService.generateKeys() genera in sequenza:

// lib/core/crypto/crypto_service.dart

Future<CryptoKeys> generateKeys() async {
  // 1. Identity Key Ed25519 — usata per firme e auth mesh
  final identityKeyPair = await Ed25519().newKeyPair();

  // 2. Master Key X25519 — long-term DH key per X3DH
  final masterKeyPair = await X25519().newKeyPair();

  // 3. Signed Pre-Key X25519 — DH key separata, firmata con identity key
  final spkPair = await X25519().newKeyPair();
  final spkPub  = await spkPair.extractPublicKey();
  final spkSig  = await Ed25519().sign(spkPub.bytes, keyPair: identityKeyPair);

  return CryptoKeys(
    identityKeyPair:        identityKeyPair,
    masterKeyPair:          masterKeyPair,
    signedPreKeyPair:       spkPair,
    signedPreKeySignature:  base64.encode(spkSig.bytes),
  );
}
// Chiavi private → Android KeyStore via flutter_secure_storage
// Chiavi pubbliche → QR code per scambio con contatti

4.2 X3DH — Extended Triple Diffie-Hellman

X3DH viene eseguito una sola volta per ogni nuova conversazione, al momento dell'invio del primo messaggio. Stabilisce una Root Key condivisa tra i due dispositivi senza che le chiavi private vengano mai trasmesse.

Formula matematica X3DH

Attore A (iniziatore) conosce le chiavi pubbliche di B dal QR:
  IK_B  = Master Key pubblica di B
  SPK_B = Signed Pre-Key pubblica di B

A genera una chiave effimera EK_A (usa e getta):
  EK_A = X25519.newKeyPair()

Calcolo dei tre DH:
  DH1 = X25519(IK_A_priv,  SPK_B)      // Master di A × SPK di B
  DH2 = X25519(EK_A_priv,  IK_B)       // Ephemeral di A × Master di B
  DH3 = X25519(EK_A_priv,  SPK_B)      // Ephemeral di A × SPK di B

Prefisso F (spec Signal): 0xFF ripetuto 32 volte
  input = F || DH1 || DH2 || DH3

Shared Secret:
  SK = HKDF-SHA256(input, salt=0x00×32, info="Invisible X3DH v1")

Root Key e Chain Keys iniziali:
  RootKey, ChainKey_send = HKDF(SK, DH_ratchet_0)

Implementazione in Dart

// lib/core/crypto/x3dh.dart

static const _f = List.filled(32, 0xFF); // prefisso spec Signal

Future<Uint8List> performX3DH({
  required SimpleKeyPair myMasterKey,
  required SimplePublicKey theirMasterKey,
  required SimplePublicKey theirSignedPreKey,
}) async {
  final ek = await X25519().newKeyPair();

  final dh1 = await X25519().sharedSecretKey(
    keyPair: myMasterKey, remotePublicKey: theirSignedPreKey);
  final dh2 = await X25519().sharedSecretKey(
    keyPair: ek, remotePublicKey: theirMasterKey);
  final dh3 = await X25519().sharedSecretKey(
    keyPair: ek, remotePublicKey: theirSignedPreKey);

  final input = Uint8List.fromList([..._f,
    ...await dh1.extractBytes(),
    ...await dh2.extractBytes(),
    ...await dh3.extractBytes()]);

  return _hkdf(input); // → SharedSecret → Root Key iniziale
}

4.3 Double Ratchet Algorithm

Il Double Ratchet opera in parallelo su due catene di chiavi che avanzano a ogni messaggio. La proprietà fondamentale è che ogni message key viene derivata, usata e immediatamente distrutta — non è mai memorizzata.

Struttura della sessione Double Ratchet

class RatchetSession {
  Uint8List rootKey;           // radice della gerarchia — aggiornata al DH ratchet
  Uint8List sendChainKey;      // catena chiavi di invio
  Uint8List recvChainKey;      // catena chiavi di ricezione
  int sendMessageNumber;       // contatore messaggi inviati
  int recvMessageNumber;       // contatore messaggi ricevuti
  SimpleKeyPair dhSendKeyPair; // coppia DH corrente per ratchet
  SimplePublicKey dhRecvKey;   // chiave pubblica DH dell'altro lato
}

Derivazione Message Key (symmetric ratchet)

// Per ogni messaggio inviato:
Uint8List deriveMessageKey(Uint8List chainKey) {
  // Message Key = HKDF(chainKey, info="MessageKey")
  final msgKey   = HKDF.expand(chainKey, info: "MessageKey",  length: 32);
  // Chain Key avanza: old chain key viene ELIMINATA
  final newChain = HKDF.expand(chainKey, info: "ChainKey",   length: 32);
  sendChainKey = newChain; // sovrascrive — no way back
  return msgKey;           // usa e poi dimentica
}

// Cifratura con la Message Key:
Uint8List encrypt(Uint8List plaintext, Uint8List msgKey) {
  final nonce = _randomBytes(12); // RANDOM per ogni messaggio (non counter)
  final cipher = AesGcm.with256bits();
  return cipher.encrypt(plaintext, secretKey: msgKey, nonce: nonce);
  // msgKey viene zeroizzata dopo l'uso
}

DH Ratchet (asimmetrico)

Ogni volta che si riceve un messaggio dal partner, viene eseguito un ratchet DH: si genera una nuova coppia di chiavi effimere X25519, si calcola un nuovo shared secret, e si aggiorna la Root Key. Questo introduce nuova casualità e garantisce il break-in recovery.

void performDHRatchet(SimplePublicKey newRemoteKey) {
  // Calcola nuovo shared secret con la nuova chiave del partner
  final dhOutput = X25519.sharedSecret(dhSendKeyPair, newRemoteKey);

  // Aggiorna Root Key e ottieni nuova Chain Key di ricezione
  final (newRootKey, newRecvChain) = HKDF.deriveKeyPair(rootKey, dhOutput);
  rootKey       = newRootKey;
  recvChainKey  = newRecvChain;

  // Genera nuova coppia DH per i prossimi messaggi
  dhSendKeyPair = X25519().newKeyPair();

  // Calcola Chain Key di invio con la nuova coppia
  final dhOutput2 = X25519.sharedSecret(dhSendKeyPair, newRemoteKey);
  final (newRoot2, newSendChain) = HKDF.deriveKeyPair(newRootKey, dhOutput2);
  rootKey      = newRoot2;
  sendChainKey = newSendChain;
}

4.4 Gerarchia Completa delle Chiavi

GENERAZIONE (una tantum, locale):
┌─────────────────────────────────────────────────────────────────┐
│  Identity Key (Ed25519)     ← firma SPK, autentica verso server │
│  Master Key (X25519)        ← long-term DH, usata in X3DH      │
│  Signed Pre-Key (X25519)    ← DH separata, firmata con IK      │
│       └─ firma Ed25519 della SPK  ← verifica autenticità SPK   │
└─────────────────────────────────────────────────────────────────┘
                           │
                    X3DH (per sessione, una tantum)
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│  Root Key                   ← mai usata direttamente           │
└───────────────────────────────┬─────────────────────────────────┘
                ┌───────────────┴──────────────┐
                ▼                              ▼
    Send Chain Key                    Recv Chain Key
                │                              │
      (per ogni messaggio)          (per ogni messaggio ricevuto)
                │                              │
    ┌───────────┴──────────┐       ┌───────────┴──────────┐
    ▼                      ▼       ▼                      ▼
Message Key 1         Chain Key 2  Message Key 1     Chain Key 2
(cifra msg → distrutta)     │      (decifra → distrutta)   │
                       Message Key 2                  Message Key 2
                       (cifra → distrutta)            (decifra → distrutta)
                            ...                            ...

PROPRIETÀ:
→ Ogni Message Key usata ONCE e poi zero-filled
→ Forward Secrecy: compromettere oggi NON espone messaggi passati
→ Break-in Recovery: dopo DH ratchet, messaggi futuri sono protetti
   anche se le chain keys correnti sono compromesse

4.5 Cifratura Media (allegati)

// lib/core/crypto/media_crypto_service.dart
// Gli allegati NON vengono inclusi nel DR plaintext direttamente
// Vengono cifrati separatamente e la chiave passa nel DR payload

Future<EncryptedMedia> encryptMedia(Uint8List mediaBytes) async {
  final key   = _randomBytes(32);    // AES-256 key random
  final nonce = _randomBytes(12);    // GCM nonce random
  final cipher = AesGcm.with256bits();
  final ciphertext = await cipher.encrypt(mediaBytes,
    secretKey: SecretKey(key), nonce: nonce);
  return EncryptedMedia(
    encryptedData: ciphertext.cipherText,
    key:   key,    // viene passata nel DR payload (cifrata E2E)
    nonce: nonce,
  );
}
// DR payload JSON:
// {"t":"image","m":"","d":"base64_ciphertext","k":"base64_key","n":"base64_nonce"}

// lib/main.dart
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();

  // SECURITY GATE: blocca su dispositivi compromessi
  final secResult = await SecurityService().runChecks();
  if (!secResult.isSafe) {
    runApp(_SecurityBlockedApp(threats: secResult.threats));
    return; // ← l'app NON si avvia
  }

  runApp(const InvisibleApp());
}

// SecurityService.runChecks() — skip in kDebugMode:
Future<SecurityCheckResult> runChecks() async {
  if (kDebugMode) return const SecurityCheckResult(isSafe: true, threats: {});
  final threats = <SecurityThreat>{};
  if (await SafeDevice.isJailBroken)           threats.add(SecurityThreat.rootJailbreak);
  if (!await SafeDevice.isRealDevice)          threats.add(SecurityThreat.emulator);
  if (await SafeDevice.isDevelopmentModeEnable) threats.add(SecurityThreat.developerOptions);
  if (await SafeDevice.isOnExternalStorage)    threats.add(SecurityThreat.externalStorage);
  return SecurityCheckResult(isSafe: threats.isEmpty, threats: threats);
}

6.3 Auto-Lock in app.dart

// lib/app.dart — WidgetsBindingObserver per lifecycle
class _InvisibleAppState extends State<InvisibleApp>
    with WidgetsBindingObserver {

  DateTime? _pausedAt;

  @override
  void didChangeAppLifecycleState(AppLifecycleState state) {
    if (state == AppLifecycleState.paused) {
      _pausedAt = DateTime.now();
    } else if (state == AppLifecycleState.resumed && _pausedAt != null) {
      final lockMin = _settingsService.autoLockMinutes; // 0 = mai
      if (lockMin > 0) {
        final elapsed = DateTime.now().difference(_pausedAt!).inMinutes;
        if (elapsed >= lockMin) {
          _profileService.logout(); // azzera cache
          navigatorKey.currentState?.pushAndRemoveUntil(
            MaterialPageRoute(builder: (_) => const LoginScreen()),
            (_) => false,
          );
        }
      }
      _pausedAt = null;
    }
  }
}

7.1 Politica di Sicurezza del Database

Principio fondamentale: Il testo in chiaro dei messaggi non viene MAI scritto su disco. Il campo decryptedText nel modello Message è marcato runtime-only e non ha corrispondenza in nessuna colonna del database. Solo il ciphertext cifrato con Double Ratchet viene persistito.

7.3 Cifratura del Database

// lib/core/database/database_service.dart
Future<Database> _openDatabase(String profileId, String pin) async {
  final path = await getDatabasesPath();
  final dbPath = join(path, 'invisible_$profileId.db');

  // Chiave derivata dal PIN con PBKDF2-SHA256, 100.000 iterazioni
  final key = await _deriveKey(pin, profileId);

  return openDatabaseWithOptions(dbPath,
    options: OpenDatabaseOptions(
      password: base64.encode(key), // SQLCipher password = chiave derivata
      version: 1,
      onCreate: _createSchema,
    ),
  );
}

Future<Uint8List> _deriveKey(String pin, String salt) async {
  final pbkdf2 = Pbkdf2(
    macAlgorithm: Hmac.sha256(),
    iterations:   100000,
    bits:         256,
  );
  return (await pbkdf2.deriveKey(
    secretKey: SecretKey(utf8.encode(pin)),
    nonce:     utf8.encode(salt),
  )).extractBytes();
}

class MainActivity : FlutterActivity() {

    super.configureFlutterEngine(flutterEngine)
    MethodChannel(flutterEngine.dartExecutor.binaryMessenger,
      "com.invisible.invisible/security"
    ).setMethodCallHandler { call, result ->
      if (call.method == "setScreenshotPrevention") {
        val enable = call.arguments as Boolean
        runOnUiThread {
          if (enable) window.addFlags(WindowManager.LayoutParams.FLAG_SECURE)
          else        window.clearFlags(WindowManager.LayoutParams.FLAG_SECURE)
        }
        result.success(null)
      } else result.notImplemented()
    }
  }
}

13.1 Struttura a 3 Layer

  "t": "text" | "image" | "file",

    "pn":    42,                           // previous chain length
    "n":     7                             // message number

}

LAYER 3 — Relay Outer Payload (ciò che vede il server):
{
  "to":      "10.7.0.8",
  "from":    "10.7.0.5",

Elementi di Novità Tecnica per Brevetto

I seguenti elementi rappresentano combinazioni e implementazioni con caratteri di novità rispetto all'arte anteriore nota. Si raccomanda valutazione formale con avvocato brevettista specializzato in software.

14.1 Sistema di Autenticazione con Identità Puramente Crittografica

Arte anteriore: Tutti i sistemi di messaggistica sicura esistenti (Signal, WhatsApp, Telegram, iMessage) utilizzano identificatori di identità registrati su server centralizzati (numero di telefono, account Apple ID, username).

Novità: Metodo per l'autenticazione e l'instradamento di comunicazioni cifrate tra dispositivi mobili basato esclusivamente su coppie di chiavi crittografiche asimmetriche (Ed25519/X25519) generate localmente, senza registrazione di alcun identificatore su server centralizzati. Il server autentica le richieste verificando firme Ed25519 senza mai memorizzare un mapping tra identità crittografica e identità reale.

14.2 Multiprofilo con Isolamento Crittografico su Dispositivo Mobile

Arte anteriore: Le applicazioni di messaggistica esistenti supportano un singolo account per installazione. Soluzioni multi-account esistenti condividono storage o credenziali tra profili.

Novità: Architettura di gestione di identità crittografiche multiple su un singolo dispositivo mobile con: (a) database SQLCipher fisicamente separati per profilo, (b) chiavi crittografiche indipendenti senza relazione matematica, (c) sessioni Double Ratchet isolate per profilo, (d) autenticazione separata per profilo tramite derivazione PBKDF2 individuale, (e) impossibilità tecnica di correlazione inter-profilo dall'esterno del dispositivo.

14.3 Integrazione Rete Mesh per Anonimizzazione IP nelle Comunicazioni WebRTC

Arte anteriore: Le soluzioni WebRTC esistenti espongono gli IP reali nei candidati ICE oppure utilizzano server TURN per il relay (che comunque conosce gli IP).

Novità: Metodo per l'esecuzione di sessioni WebRTC con anonimizzazione degli indirizzi IP mediante l'integrazione di una rete mesh WireGuard sul dispositivo mobile, dove i candidati ICE contengono esclusivamente indirizzi IP della rete overlay (10.7.x.x) non correlabili agli IP fisici dei dispositivi, eliminando sia l'esposizione IP diretta sia la necessità di server TURN.

14.4 Scambio Parametri X3DH via QR con Verifica Crittografica Integrata

Arte anteriore: I sistemi basati su Signal Protocol distribuiscono le chiavi prekey tramite server centralizzati (Signal Key Distribution Servers).

Novità: Metodo per la distribuzione dei parametri X3DH (IK, Master Key, SPK, firma Ed25519 della SPK) tramite codice QR o stringa trasportabile, con verifica crittografica della firma della Signed Pre-Key al momento dello scambio, eliminando la necessità di server di distribuzione delle chiavi e consentendo la verifica peer-to-peer dell'autenticità dell'identità.

14.5 Cifratura a Layer Sovrapposti con Privacy by Design dell'Infrastruttura

Arte anteriore: Le soluzioni VPN commerciali (NordVPN, ExpressVPN) cifrano il traffico ma non implementano E2E application-layer. Le soluzioni di messaggistica E2E non integrano VPN mesh. Non esiste un sistema commerciale che combini i tre layer.

Novità: Sistema di comunicazione mobile con triple cifratura sovrapposta dove: (a) Layer 1 = WireGuard mesh per anonimizzazione IP e cifratura rete, (b) Layer 2 = TLS 1.3 per protezione trasporto, (c) Layer 3 = Signal Protocol E2E per protezione contenuto. Il design architetturale garantisce che nessun singolo componente del sistema abbia visibilità simultanea su identità, IP reale e contenuto delle comunicazioni.
